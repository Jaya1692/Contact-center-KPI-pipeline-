Contact-Center KPI Pipeline

An interactive walkthrough: what the project does, how data flows from raw files to business KPIs, what every file is for, and a few playgrounds to try the rules yourself. Synthetic data only.

What this project does

Call centers use a chatbot to answer simple questions and hand harder ones to human agents. This pipeline takes raw contact records and answers three business questions:

KPI 1

Bot-resolution rate. How many contacts did the bot fully solve without an agent?

KPI 2

SLA-breach rate. Of the contacts handed to an agent, how many waited longer than the queue's target?

KPI 3

Intent re-training candidates. Which bot intents are failing often enough, with enough volume, to be worth improving first?

Key numbers from the generated data

2,910raw rows (two CSV files)
28quarantined (8 missing id, 8 negative wait, 6 bad date, 6 unknown outcome)
25resent duplicates removed
2,857valid contacts in Silver
448Gold daily KPI rows (14 days x 4 queues x 8 intents)
10 / 10automated tests passed (Linux, Spark 4 + Delta Lake)

Architecture (medallion: Bronze, Silver, Gold)

Runs on Databricks (PySpark + Delta Lake) or locally. Orchestrated on Databricks by a daily job with three dependent tasks.

Why each layer exists

LayerPurposeRule of thumb
BronzeKeep exactly what arrivedNever change or drop anything, so you can replay
SilverClean, typed, trusted recordsValidate, de-duplicate, quarantine bad rows
GoldBusiness answersKPIs and lists people actually use

      Walk me through the pipeline in 60 seconds.
      Raw contact files land in Bronze as text with source file and ingest time. Silver converts types safely, validates seven rules, quarantines bad rows with a reason, de-duplicates by contact id and upserts with a Delta MERGE. Gold computes daily bot-resolution and SLA-breach rates and ranks the intents that most need re-training. The same Gold logic is written in BigQuery SQL, and tests prove both give the same numbers.
      
  
      Why keep a Bronze layer instead of cleaning on the way in?
      Bronze is the untouched record. If a validation rule or KPI definition changes, you rebuild Silver and Gold from Bronze without going back to the source, and you can trace any number back to the original file.
      
  
      Why quarantine bad rows instead of dropping them?
      Dropping hides problems. Quarantine keeps the original values with a reason, so someone can fix the source, and the counts add up: raw = quarantined + duplicates + valid.
      
  
      Why try_cast and try_to_timestamp?
      Spark 4 runs in ANSI mode, where a bad cast throws an error and stops the job. The try_ versions return null, which lets validation catch the row and quarantine it.
      
  
      How is the Silver load idempotent?
      A Delta MERGE on contact_id updates existing rows and inserts new ones, so running the job twice leaves the same 2,857 rows. A test runs Silver a second time and checks the count.
      
  
      Why is the SLA breach rate divided by escalated contacts, not all contacts?
      The SLA is a promise about how fast an agent answers. Contacts the bot resolved never wait for an agent, so including them would hide real breaches.
      
  
      How do you know the KPIs are correct?
      Three ways: a test recomputes the totals with pandas, a test checks the flag rules row by row, and the BigQuery SQL is run in DuckDB and compared with the Spark result.
      
  
      How would you take this to production?
      Register Gold as Unity Catalog tables, schedule the Databricks job, alert on failures and on the quarantine rate, add schema and freshness checks on the raw files, and run the BigQuery load from a scheduled export. These parts are not done in this repository.
      
  
      What are the limits of this project?
      It uses synthetic data, and the Databricks and BigQuery deployments were not run on the real services. The re-training rule is a simple threshold, not a model.
